## 无硬件检查

固定 `N=751206`、`pulse_count=64`，使用确定性输入验证“现有八路映射 → 选路 → 软件分块 → signalsource 模板 Metadata”，不访问 `/dev/mem` 或加载硬件配置。按现有四根光纤的映射构造八路不同序列；期望值独立表达，避免测试与实现共用错误映射仍通过。

| 场景 | 预期结果 |
| --- | --- |
| 八路使用不同通道标记及样本序列，逐路选择 `0..7` | 输出只含选中通道，样本次序及 I/Q 值精确一致 |
| `channel=-1`、`8` 或非法文本，模板尺寸不符或帧容量不足 | 在硬件启动前拒绝 |
| 一个软件帧跨多个 DMA 包，或一包包含多帧 | 每 N 点输出一帧，不丢样、不重复，不依赖硬件 CPI 边界 |
| 任一必需光纤缺失、无效掩码、空指针、非法长度或对齐 | 拒绝输入，不越界读取 |
| 控制表与 BIT 混入输入 | 正确分流，不作为 IQ 样本或真实 CPI 边界 |
| 确认的采集缺口、DMA 内容变化或无效描述字 | 丢弃部分块，从下一有效采样组重新积累，不跨缺口拼接 |
| TX 全 F、非零高字、非对齐载荷 | 正确提取两个小端 uint64；TX 不参与连续性检查 |
| RX 首帧、间隔 98304、重复、前跳、回退、64 位回绕 | 首帧只建基线，后续按模 2^64 差值判断；每帧更新基线，异常不清空 CPI |
| 连续 100 次异常 | 生成 100 条完整可解析 JSONL，无 16 条样例限制，64 位值无精度损失 |
| 控制载荷不足 20 字节 | 安全拒绝并清除时间戳基线，不跨不可读控制帧比较 |
| 队列满 | 内存有界，丢弃新完成整帧并计数，已分配软件序号不回退 |
| 停止时存在不足 N 点的尾部 | 丢弃并计数，不补零，不输出半帧 |
| 模板 Metadata | 每帧 751206 点、64 脉冲；除递增的 `cpi_index` 外，与对应 signalsource 模板逐字段一致 |
| 模板轮转 | 连续至少 11 帧验证 `CPI0..CPI9 → CPI0`；整帧丢弃后按软件序号继续轮转 |
| 参数文件缺失、数组长度错误、非法数值或公共配置不一致 | 在硬件启动前拒绝，不回退到自造默认值 |
| 数据目录没有 `input.bin` | 仍可加载参数并使用实时样本，输出不混入离线样本 |

`timestamp_check_test.cpp` 覆盖时间戳规则与 JSONL，明确拒绝旧间隔 8192。`receiver_control_test.cpp` 仅替换底层硬件访问，执行真实 `PcieReceiver::poll()`，确认异常不清空部分 CPI、短载荷拒绝、双快照后的八路选路和返回样本所有权。`dma_snapshot_test.cpp` 覆盖小包顺序/大包并行复制、非对齐和尾部、重复提交、边界哨兵及停止/重复停止；线程相关测试设 15 秒超时。未接入 SDK 输出，不新增测试框架。

## 硬件联调

### 第一阶段：192.162.2.64 上的 Docker 独立采集检查

**硬件测试先在 `192.162.2.64` 上使用 Docker 运行，不连接下游 Worker，先确认 PCIe 是否持续收到有效 IQ 数据。** 本阶段不是 SDK/Sidecar 端到端验收。

- 使用本项目 `pcie_source/Dockerfile` 在构建机完成 ARM64 构建验证、push Harbor，再由目标机按 manifest digest pull 的镜像。发布记录应含标签、digest、架构和 pull 结果；不把目标机现场构建或 save/load 当作规范部署。Harbor 不可达则报告阻塞。在目标主机核对板卡、固件、物理地址及设备权限后运行。不得仅为方便默认开启全特权容器；同一板卡不能被其他采集进程占用。
- 已提供显式的“仅采集检查”模式 `--capture-only`，以 `--duration-seconds 30` 作为首次观测窗口：沿用真实接收、八路解析、选路和软件 CPI 分块路径，但不创建 SDK 输出对象、不等待 SHM 或下游连接，也不要求启动 Sidecar。
- 每完成一个 `751206` 点的软件 CPI，更新本地组帧统计后释放，不发送、不默认落盘。此处主动释放是检查模式行为，与正式运行时背压造成的整帧丢弃分别统计。
- 先检查四根光纤的有效位、接收包数和有效 IQ 字节数，再分别选择 `0..7` 观察每路样本计数和完整软件 CPI 计数。控制表或 BIT 计数增长不能算作收到 IQ。
- 周期性打印接收包数、有效 IQ 字节数、各逻辑通道样本数、选中通道、完成的软件 CPI 数、无效包、覆盖及采集丢包计数；报告观察时长和超时无数据状态。可增加有界样本摘要辅助判断，但“非零样本”不是收到数据的必要条件。

通过标准：在有输入的测试条件下，有效 IQ 和各路样本计数持续增长，选中通道能持续组成完整软件 CPI；没有未解释的解析错误或覆盖，内存有界且容器能正常停止。若没有数据，明确记录“无有效 IQ”，不能以容器存活、日志有输出或收到 BIT 信息判定通过。

> [!NOTE]
> Dockerfile 和独立采集模式已实现，并已在该主机执行。镜像版本、命令、时长及原始日志见实际验收记录。此阶段只确认采集路径有数据，不能替代通道映射、样本正确性或端到端验证。

### 第二阶段：硬件数据正确性

第一阶段通过后，再进行以下检查：

1. 按 [部署清单](../pcie_config/README.md#实施前需确认) 核对板卡、固件、地址及权限。
2. 使用可区分各通道的已知输入，验证四根光纤到八路 IQ 的既有映射及端序。
3. 分别选择 `0..7`，验证无串路、错位、I/Q 颠倒或静默覆盖。
4. 在没有真实 CPI 边界的连续输入下，仍能按 N 点输出；假 Metadata 不改变原始采样值，也不触发额外硬件配置写入。

### 新版 RX 时间戳检查

发布新镜像后，在相同独立采集模式下加 `--timestamp-errors /logs/rx_timestamp_errors.jsonl`，并将宿主日志目录绑定到 `/logs`，完整命令见 [总览](../README.md)。确认当前固件为双时间戳协议；旧序号日志不能代替此项复测。

检查 `[timestamp-check]` 的 observations、comparisons、errors、strict_continuous，再按 run_id 核对 JSONL 异常行数等于 errors。至少一次比较、所有差值等于 98304 且没有无效包才报告连续；退出码 0 本身不证明连续。异常记录保留真实前后值和描述字信息，不直接归因于发端或 IQ 丢样。

### 吞吐证据复查

```bash
python3 tests/check_capture.py \
  tests/evidence/throughput/optimized-30s-NJ0Sqt.txt \
  tests/evidence/throughput/optimized-30s-NJ0Sqt.jsonl.gz --min-msps 30.4128
```

脚本核对完整异常 JSONL 与摘要计数、实际差值、每次运行标识，并报告选中通道 MS/s。阈值从运行日志读取，兼容历史 8192 与当前 98304；不修改采集程序校验逻辑。30.4128 是标称输入速率的 99%，只作为性能门槛，不替代时间戳或样本完整性判定。

## SDK 与 Sidecar 链路

独立采集检查通过后，再退出“仅采集检查”模式，启用正式 SDK 输出并连接下游 Worker。本阶段不属于首次“是否有数据”的检查。

```text
pcie_source → Source Sidecar → 下游 Sidecar → 测试接收 Worker
```

下游使用现有 `Input<IQFrame>`，核对 `channel_count=1`、`samples_per_channel=751206`、`pulse_count=64`、软件序号、模板 Metadata 及完整样本。双方契约版本保持一致，帧容量包含 Metadata 等开销。

复用 signalsource 的 Sidecar 和下游输入配置，切换数据源镜像并补充硬件权限、板卡配置及选路后，验证输入接口无需修改。Docker 镜像必须经 Harbor 发布并按 digest 拉取，使用一致的参数数据版本；最终镜像不依赖 `input.bin`。原针对离线数据的哈希和精确算法结果校验不用于实时样本，改为核对可控输入与实际采集结果。

记录并核对启动日志中的 `synthetic_metadata=true`。下游依据部署配置知晓假参数模式，不假设帧内存在该标记。该测试证明格式和传输可用，不证明实际脉压、距离或速度结果正确，也不替代下游算法的形状检查。

## 背压下的整帧完整性检查

使用带全局递增样本索引的可校验输入，暂停下游直到输出 SHM 和本地待发送队列均满，再恢复消费。验证：

- 接收线程持续消费，内存有界；丢弃单位仅为完整的 N 点软件 CPI。
- 无硬件采集缺口时，输出序号 k 的样本仍对应输入区间 `[k*N, (k+1)*N)`，模板为 `CPI[k % 10]`。允许序号间断，不允许重复、半帧、错位或因背压重新切分。
- 对每个实际收到的帧逐样本核对连续性，不能只检查字节数；帧内无覆盖、拼接缺口或补零。
- 等待发送的旧帧与恢复后的新帧均保持原内容和序号，缓冲复用不破坏在途帧。
- 另行注入硬件覆盖/丢包：部分块被丢弃，新帧从新的可信起点积累 N 个连续样本；不再要求跨硬件缺口维持原全局区间，但必须分别记录采集错误与背压整帧丢弃。

## 故障与生命周期

验证下游停顿、断链、缓冲满、初始化失败及退出：

- 内存有界，丢帧和错误可见，不发送不足 N 点的软件帧。
- 不覆盖正在发送的帧，不访问已解除映射的地址。
- 输出阻塞可取消，接收线程可停止，资源清理完整。
- SDK 背压不被误认为硬件停止，采集覆盖能检测并处理。
