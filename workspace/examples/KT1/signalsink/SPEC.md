# Spec: SignalSink 接收与录制

模块 ID：`signalsink`。状态：**文档已整理到 Todo 草案，尚未实现；§9 中的决策尚待确认。**

本次只维护一个 SignalSink 功能，不新增 `worker-control-page` 模块或通用插件系统。
实施顺序见 [plan](tasks/plan.md)，验收任务见 [todo](tasks/todo.md)。

## 1. 已确认的目标与范围

新增末端 Worker：持续消费框架裸帧，需要时将接收的完整帧按顺序保存，供后续离线分析与回放使用。适用于符合接入契约的 IQ、脉压、RD 和自定义类型；不负责算法计算、格式转换或回放执行。

- 单机与服务器使用同一组件。默认关闭保存，不根据启动位置或是否由 Web 启动改变默认行为；关闭保存仍消费输入。
- SignalSink 随数据流运行，录制独立起停。普通停止录制不退出 Worker；关闭抽屉不停止录制。
- **录制控件由 Web 实现，放在节点抽屉的独立区域、现有 Frontend iframe 之外。** 不再替换 iframe 内的输出卡片，不插入 downstream 链路详情表。
- 保留现有预览、拓扑节点 Upstream/Downstream 水位及实际链路详情。其他 Worker 的抽屉保持原样。
- SignalSink 业务逻辑留在本目录；Web 只增加 SignalSink 专用识别、控制入口和界面。不要求其他 Worker 提供页面或控制接口。
- 单节点仍是 **Worker + Sidecar + Frontend**，不新增常驻容器。无 Web 时没有图形化录制控件，但 SignalSink 可运行、消费输入并通过显式本地控制操作录制。
- 保存位置可指定并持久保留，不静默覆盖已有文件。检测到录制缺口或无法容纳下一帧时必须明确失败，不允许丢帧后继续拼接成“成功录制”。

原始草案的八通道满配压力场景：`8 × 15.36 MHz × 4 B = 491,520,000 B/s`，即 **491.52 MB/s、29.4912 GB/分钟**，不含帧头、Metadata 和文件开销。它不是已经达到的能力，也不是当前实际 Source 配置的证据。

**2026-10-08 审阅注：**用户质询该指标来源后，已明确不能把上述假设当成当前部署必须承载的已确认输入。A8 保留该压力场景记录；实际验收速率仍须按运行通道数、采样率、样本格式和帧开销确认。当前实现/测试进度见 [验证记录](tests/acceptance.md)，存储诊断见 [吞吐结果](tests/throughput-results.md)；本稿其余“尚未实现”等叙述为初版规划时状态。

不包含：通用 Worker 控件平台、独立 Worker 控制网页、Frontend 录制逻辑、MAT 转换、压缩、索引数据库、历史录制管理平台、中间节点旁路录制、PCIe 八通道采集改造。

## 2. 架构与当前缺口

```text
数据：上游 → Sidecar → Ring → SDK → SignalSink → 有界待写队列 → 磁盘
预览：Sidecar 抽样 → 现有 Frontend → Web 中的原 iframe
控制：Web 的 SignalSink 区域 → 已有 SSH 管理通道 → SignalSink 本地控制入口
```

控制通路是本稿的最小实现建议：复用 Web 的 SSH 会话，经固定的 `docker exec` 命令调用 SignalSink 自带控制子命令；只传命令和小体积状态，不传录制数据或预览。CLI 与同容器内的接收进程通信，不启动第二个接收器。无需 Worker HTTP 服务、新控制端口、证书或新账号。

### 已核实的限制

| 现状 | 对实施的约束 |
|---|---|
| [SDK 公开接口](../../../infra/sdk/include/data.h) 只有类型化 Input/Frame，完整 Envelope 不公开 | 不能通过 metadata()/data() 重建帧，宣称逐字节原样保存；必须先解决受支持的裸帧读取入口 |
| [SDK 读取循环](../../../infra/sdk/src/sdk.cpp) 会等待输入或 Ring shutdown，没有公开超时/取消接口 | 正常停止录制必须不依赖下一帧到达；进程有界退出还需确定读取取消方案 |
| [通用 Envelope](../../../infra/common/raw_frame.hpp) 存在于基础设施内部 | 不复制帧定义，也不把 SignalSink 写成绕过 SDK 的临时 Ring 消费者 |
| [Web 规划器](../../../infra/web/internal/orchestration/planner.go) 按具体 type/version 匹配 Worker | 不能假设现有 worker/v2 已支持通配输入；通用接收的部署绑定需单独确认 |
| 当前 PCIe Source 不等于八通道同时输出 | 合成输入性能验证与真实八通道端到端验证分开，不借本项目修改 PCIe Source |

**SDK 和接入契约缺口是实施前置条件，不是已解决的事实。** 若必须扩展 SDK/契约，先确认最小范围，保留旧调用方式和类型校验；不得悄悄退化成只支持 IQ 的实现。

## 3. 接收与录制行为

### 数据正确性

- SignalSink 是该 Worker 输入端口的正常消费者，不增加第二个消费者，不从有损预览流取录制数据。
- 保存收到的 Envelope、Metadata、Payload 及其边界和顺序；保留未知字段，不重新编码，不写入 SHM Slot 的空闲填充或未初始化内存。
- 校验实际可读长度、声明长度和端口约束后再拷贝/入队。自定义 Metadata 作为不透明字节保存，不增加业务解析插件。
- 一条输入链路一次绑定一个明确 type/version；需要同会话混合类型的要求暂不默认成立，见 D3。
- 必须有队列容量上限，计入待写、正在写入及分配开销。释放输入 lease 前取得合法的数据所有权；不能排队裸指针后复用 Slot。

### 状态与故障

| 状态 | 行为 |
|---|---|
| `idle` | 消费输入但不保存；允许显式开始 |
| `starting` | 检查路径、空间和资源；禁止重复开始 |
| `recording` | 接收完整帧进入有界队列并按序写入 |
| `stopping` | 确定截止帧后不再入队，排空已接受的数据并收尾；继续消费后续输入 |
| `failed` | 记录失败原因和有效边界，不自动续录；重新开始是新的录制会话 |

开始和停止以 Worker 确认的帧边界为准，不声称精确对应浏览器点击时间。停止请求带录制 ID，不能误停另一次录制；响应丢失时先查状态，不盲目重发开始。不会因没有新输入而一直无法停止录制。

**建议的异常策略，待 D1 确认：**队列容量不足、可检测的缺口、磁盘空间不足或写入失败，只停止本次录制并报错，继续正常消费输入，不主动停止 Sidecar 或整条链路。Ring 损坏/输入不可读不能假装“仍正常消费”；应报告节点故障。该策略不能保证磁盘故障下绝对零抖动或保住尚未落盘的数据。

## 4. 保存与连续性边界

### 最小保存方案（建议）

- 一个录制会话只顺序写一个数据文件，不做滚动、自动清理或续写旧文件；需要重开时创建新会话。
- 最小文件封装只解决格式识别/版本、原始帧边界和完成标记，不改变传输协议。正式布局在实施前冻结，不复制另一套 Envelope。
- 使用排他创建，不能只按时间戳假定文件名唯一。写入中的文件标记为未完成；成功收尾并完成同步后才标记完成。
- 正确处理短写、EINTR、ENOSPC、EIO 和同步失败。异常文件保留有效前缀并明确标为失败/未完成，不伪造完整帧或成功结尾。
- 普通停止的成功回执要晚于数据及必要文件/目录元数据同步。异常退出/断电的损失窗口尚未约定，不承诺零丢失或自动修复。

### 路径与持久化

部署时为 SignalSink 挂载专用宿主保存根目录，容器内统一为 `/captures`。Web 中选择该根目录下的子目录，不将浏览器路径直接解释为任意宿主挂载或 Shell 命令。

Worker 校验路径穿越、符号链接逃逸、写权限及实际目标卷空间。上次选择的目录保存在该持久卷的小配置文件中，重建容器后仍可恢复，但**恢复目录不等于恢复录制**。修改根挂载目录属于部署操作，不能靠录制按钮动态扩大访问范围。

### 连续性不能混淆

1. **保存完整性**：本会话接收并接受录制的帧是否全部、按序、逐字节保存，可由 SignalSink 验证。
2. **上游帧缺口**：仅能按已确认的序号/代际/缺口标记契约检查，不能自行假设所有类型的 frame_id 都连续加一。
3. **采样连续性**：依赖采集端提供可信信息；完整 Envelope 或单调帧号不能证明硬件采样无损。

没有必要依据时显示“采样连续性未验证”，不是“无丢失”。是否允许在这个条件下起录，或必须拒绝起录，见 D2。

## 5. Web 控制与显示

只提供三种 SignalSink 操作：**查询状态、开始录制、停止录制**。不暴露任意命令执行接口。

- 复用现有登录、节点授权、SSH 指纹、CSRF 和错误提示；目标为已检查/已部署的对应 Worker，不由浏览器提供容器 ID 或控制地址。
- 通过明确的 SignalSink 组件标识及实际运行身份识别，不能仅凭镜像名包含 signalsink 或 role=sink；其他 Sink 校验器不显示控件。
- Web 抽屉在节点摘要之后提供独立录制区域；现有 iframe 和链路信息保持原样，不插入 iframe DOM，不新增 Frontend 显示模式。
- 状态为 Worker 的实际状态。只在该区域打开时低频查询，建议 1 秒一次、同节点不堆积请求；网络慢时不补发积压轮询。
- 请求和本地控制响应有界；等待网络/磁盘不持有全局 Web 管理锁或阻塞 Worker 数据循环。
- Web/浏览器断开、登录过期或重启，停止界面查询，不隐式停止录制；重新登录后查询恢复实际状态。
- 超时、离线、状态过期显示“未知/未上报”，禁用会改变状态的按钮；不能显示为 0% 或点击即成功。Web 断连也不证明操作未执行。

最小状态字段：录制 ID/状态、目录、已写帧数和字节数、运行时间、待写队列已用/容量、目标卷总量/已用量/进程可用空间、连续性结论和最后错误。跨 JSON 的 uint64 计数使用十进制字符串。

队列水位不是 Upstream Ring 水位；磁盘水位不是本次文件大小或带宽利用率。统计失败时显示未知。录制失败后明确提示原因，不自动重新开始。

[旧 HTML 草稿](recording-control-prototype.html)仅保留作控件内容参考；其中“替换输出卡片”的位置说明已作废，不作为当前布局验收依据。本轮不修改该原型。

## 7. 约定命令

**以下为实现后的目标命令，当前不存在可构建的 SignalSink。** 在已安装受支持 SDK 的原生 ARM64 构建环境、仓库根目录执行：

```bash
test "$(uname -m)" = aarch64
cmake -S workspace/examples/KT1/signalsink -B build/signalsink -DBUILD_TESTING=ON
cmake --build build/signalsink --parallel
ctest --test-dir build/signalsink --output-on-failure
```

在已接入 Sidecar 的 Worker 容器内，拟定运行/控制接口：

```bash
/app/signalsink --capture-root /captures --queue-bytes 536870912 --min-free-bytes 1073741824
/app/signalsink control status
/app/signalsink control start --directory run-a
/app/signalsink control stop --recording-id RECORDING_ID
```

第一条只启动接收，不能默认起录。后续命令连接同容器正在运行的进程；不能额外打开数据 Ring。数值是 D4 的候选值，`RECORDING_ID` 必须取自实际状态。

Web 验证在既有原生 ARM builder 环境执行，先生成嵌入资源：

```bash
cd workspace/infra/web
(cd frontend && npm run build && npm test)
go test -timeout 90s ./...
go vet ./...
CGO_ENABLED=1 go test -timeout 90s -race ./internal/orchestration
```

发布沿用现有 ARM 构建/Harbor 流程及已验证 digest，部署不现场编译。不新增发布工具链；新 Worker 的首次拉取入口与已有发布脚本是否需适配要核实，不假定当前 Web 已能在空节点首次安装任意 Worker。

## 8. 验收与修改边界

| ID | 必须证明的结果 |
|---|---|
| A1 | 默认不保存仍持续消费；显式开始、停止、无输入时停止和重复/迟到命令行为可预测 |
| A2 | IQ/PC/RD/受支持自定义帧的原始字节、边界和顺序一致；未知字段不丢失；坏长度被拒绝 |
| A3 | 队列容量、lease 生命周期有界；慢盘/溢出风险/写入失败触发明确失败，不静默续录或伪造成功 |
| A4 | 路径不逃逸、不覆盖文件；挂载与目录选择持久化；正常收尾及故障前缀可独立校验 |
| A5 | 状态、录制队列和实际目标卷水位准确；状态未知不显示零，不能伪称采样连续 |
| A6 | 控件仅出现在 SignalSink 的 Web 抽屉独立区域；无 Web 的单节点数据链及原 Frontend 预览正常 |
| A7 | 关闭/重开抽屉、Web 重启/会话过期不改变录制；其余节点、算法和主链容器不因控件操作重启 |
| A8 | 原生 ARM、实际目标存储持续承载 491.52 MB/s 载荷及额外开销，正常停止后文件校验通过；不以 page cache 峰值或 tmpfs 冒充实际落盘 |

测试先用小型确定性帧与故障注入，复用 CTest/Go/Vitest；不依赖每次都跑硬件长测。吞吐测试是单独硬件验收，记录目录/文件系统、设备、输入速率、队列峰值、写入及同步时间、持久化字节数。建议先验收 60 秒载荷，再按确认的录制时长扩展；未确认前不把 60 秒结果当成长录制保证。

- **Always**：先明确 SDK/契约，再实现；保留数据完整性校验、输入边界、故障状态和既有 IPC；所有应用按 ARM64 验证；文档与测试可追踪。
- **Ask first**：SDK/ABI 或通用接入契约变更；修改 Sidecar/Ring/已有算法；新依赖；修改已有公共构建/发布脚本；磁盘挂载、覆盖已有部署；D1–D5 的关键行为。
- **Never**：修改或复制裸帧协议以绕过接口缺口；以预览代替原始数据；无限缓存；静默丢帧后宣称连续；自动覆盖/删除录制；顺带建设通用插件框架或 PCIe 八通道输出；本轮写实现、部署或提交。

## 9. 待确认决策与实施门槛

| ID | 本稿的最小建议 | 状态/影响 |
|---|---|---|
| D1 异常策略 | 只停止录制，继续消费可读输入；不自动续录或停止整链 | 尚未获得明确确认；影响状态机和故障验收 |
| D2 连续性 | 保存完整性必须保证；无采样证据时显示未验证；仅按明确契约识别缺口 | 是否允许这种输入起录、具体序号/代际规则需确认；不能替用户定义为硬件无损 |
| D3 接入方式 | 获得受支持的裸帧读取/取消能力；部署时把 SignalSink 绑定到上游具体 type/version，其他 Worker 校验不放宽 | 当前 SDK/worker 契约不足；最小扩展及修改范围需批准；首版不默认混合类型 |
| D4 缓冲与存储 | 512 MiB 有界队列、1 GiB 可用空间保留作为起点；可按实机调节；一个会话一个文件，手动起停 | 参数、目标目录/设备/时长、磁盘阈值、是否需要定量停止或滚动均待确认；空间预算须覆盖排队/在途帧 |
| D5 持久性 | 正常停止等待同步成功；崩溃保留未完成文件，不自动续录；不承诺逐帧抗断电 | 文件封装、完成标记、同步周期、正常退出期限及允许损失窗口需确认 |
| D6 轻量控制 | Web 经既有 SSH 调固定 CLI；本地控制不阻塞数据循环，无 Worker HTTP 服务或新端口 | 本稿方案建议；若要求直接 HTTP 控制，先修订计划，不两套并行实现 |

已批准的是“SignalSink 专用、Web 独立区域、KISS、单节点架构不变”的方向；上表不能因写入 Todo 就视为默认获批。**本轮按要求交付 SPEC/Plan/Todo 草案；实现必须先关闭相关门槛。**
