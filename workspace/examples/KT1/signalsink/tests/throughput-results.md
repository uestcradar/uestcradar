# SignalSink 真盘诊断：未达到持续流盘目标

日期：2026-10-08。**八通道压力场景的 T12 / A8 未通过；当前实际部署的目标速率待确认。** 491.52 MB/s 来自草案满配假设，不是当前实测 Source 输出。这不是完整链路、RDMA 或真实 PCIe 八通道验收。

## 环境与边界

- 原生 ARM：`192.162.2.64`，aarch64；不是 QEMU。
- 目标：`/dev/sda4`、ext4、`HQ_SSD_64GB`，SATA 链路协商为 6.0 Gbps。
- 测试根目录：`/root/workspace/captures/signalsink-test-mEPM4C`。
- 初始可用空间约 27 GB；60 秒载荷约 29.5 GB，不能安全容纳，未强行运行。
- 只运行隔离测试容器；未部署新 Web、未操作原有 Web 容器，未发布镜像。
- 未改磁盘调度器、全局 VM 参数、驱动、设备映射或硬件配置。
- 读取到的 VM 设置：`dirty_ratio=60`、`dirty_background_ratio=10`、`dirty_expire_centisecs=3000`。这些是已有设置，不是测试修改。

## 判定口径

目标载荷 **491,520,000 B/s**。夹具每帧 8 通道 × 32,768 个 CS16 样本；468.75 帧/秒。计入 Envelope、IQ Metadata 和文件长度字段后约 **492.56 MB/s**。

必须分别报告输入时间、录制到最终同步完成时间和实际文件校验。`write()` 返回、录制队列很低、文件长度增加，都不能证明已经持久化。

`benchmark.py` 现在将包含最终同步的载荷吞吐纳入退出码判定，允许 1% 调度误差；未达标返回非零。功能烟测明确排除性能验收。最早 `disk-30s.json` 的 `success=true` 只表示文件完整性；其 300 MB/s 指标**不构成性能通过**。

## 实测

MB/s 为十进制；短实验不是长期 SSD 上限测量。

## 分层证据

1. **延迟回写确实存在。** `baseline-6s.metrics` 显示前几秒磁盘写入接近零，脏页增至约 2.77 GB；随后物理写入约 351–484 MB/s。解释了停止时集中同步，但不能据此证明长期 491.52 MB/s。
2. **不是仅仅 SDK 或录制队列开销。** 绕过 SDK/SignalSink，对同一文件系统写高熵数据并 `fsync`：2 GiB 普通连续写约 142 MB/s，`O_DIRECT` 约 101 MB/s。
3. **预分配不是充分修复。** 1 GiB 预分配后直接写约 311 MB/s，覆盖同一测试文件约 327 MB/s，仍未达目标。
4. **短测结果波动明显。** 高熵/全零/高熵三次 512 MiB 直接写分别约 308/544/104 MB/s。数据模式、闪存缓存和测试次序可能影响结果；目前不能把差异单独归因于压缩、SLC 缓存或温度。
5. **增加 I/O 深度没有改善。** 同一预分配测试文件、1 GiB 高熵数据、4 MiB 对齐直接写，深度依次 1/4/8/1，含同步分别为 **323.20 / 320.82 / 325.93 / 327.60 MB/s**。排除了本次测试中“单个同步写队列深度不足”作为主要原因；没有依据引入线程池或 io_uring。
   - 清理本轮合成捕获、恢复约 27 GB 可用空间后，重复深度 1/4/8/1，结果为 **194.58 / 194.60 / 194.39 / 195.26 MB/s**。设备状态有波动，但增加深度仍无改善；不能将单次短测定为型号的绝对上限。
6. **提前回写不是无风险加速。** `sync_file_range(WRITE)` 在本次负载下会使写线程等待，接收队列最终溢出。128 MiB 候选缩短恒值短录制的总时间，但高熵测试失效，故未保留在生产代码。

当前结论：**这块系统盘及当前文件系统/负载组合尚不能承担已要求的持续吞吐。** 尚未测得 SSD 裸设备的绝对上限，也未证明其他更快存储上会有相同限制。增加用户队列或依赖更多脏页只延后背压，不能制造持久化带宽。

## 复现

使用新 SDK 安装编译 SignalSink，并在原生 ARM 的实际磁盘目录运行：

```bash
python3 workspace/examples/KT1/signalsink/tests/benchmark.py \
  --worker build/signalsink/signalsink \
  --producer build/signalsink/signalsink-throughput \
  --capture-root /absolute/real-disk/test-root --seconds 6
```

目录必须已存在；脚本检查容量，拒绝把 tmpfs/overlay/ramfs 当真盘。根目录只能供本次测试使用，不能指向其他正在运行的 SignalSink；控制变更前校验进程 ID。

证据在 [`evidence/storage/`](evidence/storage/)。其中 `*_probe.py` 是诊断脚本，路径绑定本次测试目录，仅创建/删除自己的排他测试文件；不是生产服务。`writeback128-trial.patch` 仅供复现失败候选，**未应用**；16 MiB 试验仅改变其批量常量。

原始报告保留失败与历史路径。本轮大体积合成捕获在独立校验并保存摘要后删除，恢复约 27 GB 可用空间；保留所有 JSON 报告，未清理用户录制、旧镜像或回退容器。

## 已授权的单次 TRIM 验证

SMART 自检状态上报 PASSED，属性 194 上报 33°C；未见本轮 SATA/文件系统错误，检查的根及 user.slice cgroup 没有写入 BPS/IOPS 限速。以上不等于证明设备没有内部节流。

设备支持 discard，但挂载没有 `discard`，`fstrim.timer` 为 disabled、无定时任务。用户明确批准后，于 2026-10-08 04:53:47 UTC 执行一次 `fstrim -v /`，工具报告回收 **30,879,498,240 字节（28.8 GiB）**。未启用定时任务、未改挂载或 VM 参数。

相同直接写探针深度 1/4/8/1 复测为 **314.90 / 329.54 / 327.71 / 327.77 MB/s**，较紧邻 TRIM 前约 195 MB/s 的一轮提高，但仍不满足目标。实际高熵录制 6 秒耗时 **21.08 秒**，含同步约 **139.95 MB/s**，与之前 141.31 MB/s 接近。2,813 帧、2,955,832,888 原始字节逐字节验证通过。

结论：TRIM 改善了本次直接写短测，但**不是录制端到端吞吐不足的充分修复**，不能据此通过 T12。新增证据为 `trim.txt`、`queue-depth-after-trim.jsonl`、`entropy-after-trim-6s.json`。本次合成捕获校验后清理，可用空间恢复约 27 GB；原有 Web 保留运行，定时 TRIM 仍为 disabled。

## 原生 fio 与持续写入定位

进一步排除 Python 开销、同步调用与浅队列：使用服务器现有 `fio-3.22`、原生 aarch64 `libaio`，只写本次排他创建的测试文件。参数为 `direct=1`、`bs=1m`、`fallocate=posix`、`refill_buffers=1`、`scramble_buffers=1`、`end_fsync=1`；写后完整读取并做 CRC32C 校验。未写裸设备，未关闭同步或校验。

| 原生 fio 场景 | 写入 | 校验读取 | 其他观测 |
|---|---|---|---|
| 4 GiB，深度 1 | 197.69 MB/s | 459.45 MB/s | 退出码/错误均为 0 |
| 4 GiB，深度 32 | 205.56 MB/s | 559.60 MB/s | 深度 32 占约 99.24%；设备利用率约 99.73% |
| **16 GiB，深度 32** | **106.52 MB/s，写入耗时 161.28 秒** | **550.53 MB/s** | 17,179,869,184 字节全部写入和读取校验；设备利用率 100%；用户/系统 CPU 约 7.78%/0.41% |

每秒带宽记录进一步表明：前约 4 秒写入约 290–331 MB/s，随后降速。**第 10–30、30–60、60–120 秒的平均写入分别约 101.19、101.20、101.20 MB/s。** 这不再只是 1 GiB 短测波动；持续阶段不足满配载荷要求的四分之一。

该结果支持：瓶颈位于当前设备/存储路径的持续写入能力，而不是 SignalSink 的帧解析、Python 解释器或缺少异步 I/O。高深度已生效、设备持续忙、CPU 未饱和，读取能达到 SATA 高吞吐。先快后慢的形态符合设备写缓存耗尽后的退速，但未获得厂商证据，不能把具体 SLC/固件机制当作已证明事实，也不宣称测出了所有可能条件下的理论极限。

诊断还有一个口径问题：限速输入的 6 秒录制加最终刷盘时间，不等于介质稳态带宽。其结果适合检查该次完整录制的结束延迟，不能单独用来确定设备上限；因此本轮以原生持续写入对照补充判断，而非继续只看 140 MB/s。

代码盘点：`pcie_source/src/options.hpp` 默认选择通道 0，`cpi_templates.hpp` 设置 `channel_count=1`；`main.cpp` 的普通 SDK 输出仍明确报未实现，仅有 capture-only 诊断。当前节点只运行 Web，没有实时 Source 可以据此测出实际输入速率。因此不能宣称当前业务必然需要八通道的 491.52 MB/s，也不能把模板采样率当作已经验证的硬件实际采样率。

fio 原始 JSON、每秒带宽日志及脚本均在 `evidence/storage/`。所有 fio 测试文件已经移除，磁盘恢复约 27 GB 可用；原 Web 保持运行。未修改生产写入代码来掩盖存储带宽不足。
